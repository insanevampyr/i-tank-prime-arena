## Task 36K-Pass1 — browser infrastructure; gameplay remains blocked

`character_browser_store.js` uses an application-specific IndexedDB database (`itank-prime-arena.character-profiles`, database layout version 1). This is independent of character Save Contract V2 and simulation schema 12, which are unchanged. Exact canonical contract envelope strings are retained, never parsed/re-serialized as replacement character documents. The transport checks envelope version/checksum/profile/namespace; `CharacterBrowserPersistence` additionally reuses the existing coordinator's authority, hydration, receipt, replacement, item-acquisition and continuity checks. `CharacterBrowserStorage.inspection` decodes history with the original full Godot contract.

The asynchronous boundary is `CharacterBrowserStorage.begin(operation, arguments)` / `poll(job)` and `CharacterBrowserPersistence.begin_commit(...)` / `poll()`. Status is `pending`, `verified_committed`, `failed`, `unavailable` or `recovery_required`. A queued operation has `success=false`. The host pumps operations outside combat; there are no blocking waits, simulation ticks, speculative application, retained Godot callbacks or file-clock dependencies. `begin_commit(..., reconcile_only=true)` reads and reconciles an exact retained proposal without issuing another publication. Do not infer that a failed read means a missing profile.

Three object stores contain immutable generations, immutable transaction identities and the current-generation pointer. One readwrite transaction compares the actual expected generation and adds the generation/receipt plus pointer atomically. Conflicts/abort do not publish any of them. Strict durability is requested where supported, not represented as a universal hardware guarantee. A successful publication waits for transaction completion, then a **new readonly transaction** verifies exact document bytes, generation, transaction and history/head agreement. An exact retry or explicit reconciliation returns the existing generation without replaying rewards. A reused transaction with different content is rejected. Older verified generations are retained; corrupt/unsupported history blocks writes and requires review rather than silent rollback, deletion or replacement with a new character.

Every writer must acquire an exclusive native Web Lock named for its database/profile. Acquisition is nonwaiting (`ifAvailable`); contention and missing Web Locks fail closed. `transfer(profile, owner, next_owner)` hands an idle lease to a candidate in place without releasing it; the former owner loses permission. Release/transfer is rejected during publication. Explicit release, store close or browser context termination releases the lease. Future gameplay integration must hold it throughout the authorized session, retain it across RETRY/RETURN candidate validation, and transfer only when the candidate can take ownership. Pass1 tests exercise the lease mechanism; actual playable Web candidates remain disconnected. NORMAL `prod_` and DEV NORMAL `dev_` identities have separate records and locks; TEST has no production namespace.

The JavaScriptBridge JSON job map is bounded (32 outstanding jobs per handle); terminal jobs are removed when polled. `export_presets.cfg` includes only the required transport JS. The desktop synchronous storage/coordinator/session APIs and all live Web guards are unchanged. No production browser profile was created during validation.

## Task 36J-Pass2: isolated transaction coordinator

`CharacterPersistenceCoordinator` is not called by gameplay. `prepare(payload, settlements, transaction_id, expected_generation, expected_checkpoints)` makes an immutable-by-copy proposal with canonical document bytes. `commit(prepared, source, profile_id, rules_revision, verifier)` revalidates Pass1 hydration and trusted lineage, obtains a separate host authorization bound to the entire transaction proposal, checks expected durable generation/checkpoints, and delegates publication to the existing storage writer. It rereads exact bytes before acknowledging. `reconcile(...)` is read-only and locates the original transaction without regenerating rewards. No actual production verifier/profile provider is installed; isolated tests supply the authority fixture.

The existing character envelope v2 now recognizes an explicit optional `settlements` field. Each settlement receipt is version 1, with `profile_id/run_id/wave_id/claim_id`, kind (`xp`, `currency`, `item`, `purchase`) and exact content. Receipt/effect identities must be unique; an acquisition origin cannot be claimed again under another item ID. The complete profile, immutable old receipts and new receipts are published in one generation, protected by the existing character checksum. XP/purchase receipts must cover the saved award/purchase histories and exact amounts. Every owned item requires an original acquisition/admission receipt, including starting possessions; the coordinator never invents those receipts. Existing instance quantities cannot grow, consumed instances cannot be resurrected through old receipts, and unsupported shield repair cannot be smuggled in as a save. These are fail-closed persistence capability boundaries, not new combat/repair rules. Live ownership adapters must provide source-valid evidence before activation.

An exact transaction retry returns the existing committed generation; different bytes under the same transaction conflict. An old successful transaction can be reconciled after later generations exist, but the result identifies the newer generation separately and must never be treated as permission to load the older proposal. Missing/corrupt history yields explicit uncertain/recovery-required status rather than claiming success. A stale generation or another writer at the proposed generation conflicts. Storage's existing exclusive writer lock and locked sequential-generation check remain the final lost-update guard; preflight alone is not treated as CAS. Publication is not retried automatically after an ambiguous acknowledgement.

Read-only `inspect_profile` exposes validated generation records, pending-write/lock flags and rejected files. Noncontiguous generations and repeated historical transaction IDs block coordinator writes/reconciliation. Future inner character versions AND outer storage versions prevent fallback. Corrupt-current reads may still expose an older valid backup, but the coordinator refuses to write across damaged history. Pending files and stale locks are never deleted or promoted. No repair, lock stealing, automatic rollback or filesystem power-loss guarantee is introduced. An already verified historical transaction can be acknowledged with an explicit recovery flag if a separate pending write/lock exists; subsequent writes stay blocked.

Web production writes remain **BLOCKED** (`web_write_coordination_unverified`). No verified IndexedDB acknowledgement or cross-tab CAS adapter exists. ## Interface and publication

- `get_storage_status()` reports desktop readiness or an explicit Web/unconfigured-root gate.
- `write_profile(profile_id, payload, transaction_id)` validates v1 through `CharacterSaveContract`, serializes canonical JSON, acquires a profile writer directory, checks durable transaction receipts and current generation, writes `write.pending`, flushes/closes, rereads/validates, renames to an immutable generation file, and rereads the result.
- `read_profile(profile_id)` returns the highest valid generation with exact character document text, payload and transaction ID. Corrupt generations are listed explicitly when an earlier valid generation is returned. It never creates empty progression on failure. Unknown future versions fail closed instead of downgrading.

The application root is `user://character_documents`. Profile and transaction IDs accept only lowercase ASCII letters, digits, underscore and hyphen, maximum 64 characters. Profile identity must equal the character ID. Test roots are restricted to unique subdirectories of `OS.get_cache_dir()/itank-storage-tests/`; tests never write live `user://` saves. No arbitrary caller-selected production paths or path separators are accepted. This protects application path construction, not hostile OS-level modification/symlinks of the save directory.

Generation files retain transaction IDs as durable receipts. All previous generations are retained in this bounded infrastructure pass; pruning is deferred because it would require an approved durable receipt-compaction policy. Initial generation must be one; later writes must pass the contract's identity, next-generation and secured-checkpoint checks. Loading returns a whole document; it does not merge XP/items or re-execute purchases. The layer validates structural data only and does not authorize rewards or validate Prime purchase legality.

## Safety and limits

The active document is selected from complete generation files rather than overwriting one pointer file. Same-directory rename publishes the candidate while all previous valid files remain untouched. This is a deliberate implementation of replacement through generation selection, without changing the character v1 format. The outer storage wrapper v1 contains transaction ID and the exact character document; the character checksum detects document corruption, not malicious editing or authenticated receipts.

Failed temporary writes, verification failures, existing pending files, corrupt generation history and writer-lock contention return meaningful failure codes. A pending file is ignored by reads and blocks writes until explicit future recovery review; it is not automatically promoted or deleted. Corrupt current/backup files remain intact for inspection. A returned older valid generation is marked recovery and cannot be silently written over the damaged history. A stale writer lock also requires review; no time-based lock stealing exists.

Exclusive directory creation guards cooperative desktop writers using this coordinator. It is not a guarantee against another program editing files, copied rollback saves, symlinks or a filesystem with different semantics. Errors after publication may leave a committed generation despite an unsuccessful acknowledgement; the caller must reread and inspect its transaction ID, never invent a new reward or blindly retry under a new transaction. Flush/close/rename checks are tested normal filesystem operations, not a proven power-loss transaction or fsync guarantee. No automatic backup rewrite occurs.

Web reads can inspect available virtual `user://` data. Writes return `web_write_coordination_unverified` with `state=unverified` and the official `OS.is_userfs_persistent()` availability flag. That flag does not confirm an asynchronous IndexedDB commit. No Web save success/durability is claimed, and cross-tab races are blocked by disabling Web writes. A future browser adapter requires tested synchronization completion and an enforceable per-profile writer policy before activation. Private mode, quota, eviction, cleared browser data and origin/device changes remain storage-loss risks. No cloud backup exists.
